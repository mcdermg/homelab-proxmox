# OpenTofu Proxmox Homelab

OpenTofu + Ansible configuration for Proxmox VE homelab infrastructure including K3s cluster, LXC containers, and Cloudflare Tunnel.

## Infrastructure

**LXC Containers (TurnKey Linux, except the plain Debian 13 ones):**
- LibreSpeed (CT 111) - Speed test (`librespeed/speedtest-rust`), Debian 13
- Pulse (CT 112) - Proxmox cluster monitoring, Debian 13. Login: `admin` / `pulse_admin_password` from `terraform.tfvars`. Alerts (warning and up) go to Slack via `slack_alerting_webhook`; thresholds are set by the role from `pulse_alert_config`
- Cloudflared (CT 113 on pve02, CT 118 on pve01) - Cloudflare Tunnel client, two replicas of the same tunnel so it stays up with one node down
- Bind9 (CT 115 on pve02, CT 119 on pve01) - DNS server, both rendered with the same zones (`ns1`, `ns2`)
- Postgres (CT 116) - Database server
- Gitea (CT 117) - Git server

**K3s Cluster:**
- 2 control plane VMs (Proxmox VMs 210-211)
- 2 worker VMs (Proxmox VMs 215-216)
- 2 Raspberry Pi nodes (external hardware, Pi 4 `.241` and Pi 3 `.242`)

**Services:**
- Cloudflare Zero Trust Tunnel with automatic DNS records, including one route per Proxmox node (`pve01`, `pve02`) so the cluster stays reachable if one node is down. `tf output dns_records` lists them all.
- Internal DNS via Bind9 (`homelab.local`): A and PTR records for every Proxmox node, LXC, k3s VM and Pi are generated by OpenTofu (`local.bind9_records`) and passed to the bind9 role through `hosts.ini`. A playbook run updates the zones on both servers
- Your SSH key (`ssh_public_key_file`) is injected into every container and VM, and Ansible logs in with it

## Ansible Operations

**Initial Bootstrap:** `ansible/playbook.yaml`
- Configures TurnKey containers via Proxmox `pct` commands, each play running on the node that holds its container (`[postgres_node]`, `[gitea_node]`, `[bind9_node]`, `[cloudflared_node]` in the generated `hosts.ini`; the last two have an entry per container, named `<node>-ct<id>`)
- Sets up SSH keys and root passwords via inithooks
- Installs and configures services (Bind9, Postgres, Gitea, Cloudflared)

**System Updates:** `ansible/update.yaml`
- Updates both Proxmox nodes, all LXC containers, and every k3s VM and Pi (the inventory lists whatever is in `k3s_vms`)
- Runs in batches of 3 to avoid resource bottleneck
- Use `--limit` to target specific groups or hosts

```bash
ansible-playbook update.yaml                    # Update everything
ansible-playbook update.yaml --limit proxmox    # Proxmox nodes only
ansible-playbook update.yaml --limit k3s_pis    # Raspberry Pis only
```

**Monitoring:** plays tagged `monitoring` in `playbook.yaml` (Pulse, node_exporter on the Proxmox nodes, the Pulse agent on the Pis) and `k3s.yaml` (Secrets for the cluster's Pulse agent token and the k3s Alertmanager's Slack webhook)
- The `pulse_agent` role creates each agent's Pulse token through the Pulse API and hands it straight to the agent; nothing is stored in tfvars. A rerun replaces the token on whichever side was rebuilt

```bash
ansible-playbook playbook.yaml --tags monitoring    # Only the monitoring plays
ansible-playbook k3s.yaml --tags monitoring         # Only the two Secrets; skips the k3s install
```

**k3s Cluster:** `ansible/k3s.yaml`
- Imports the site playbook from the official [k3s-ansible](https://github.com/k3s-io/k3s-ansible) collection, pinned in `ansible/requirements.yaml`, then labels the agents as workers
- Nodes come from the `server` and `agent` groups in the generated `hosts.ini`: the control VMs plus the Pi 4 (`pi-control`) are servers (embedded etcd, the first one initialises it), the worker VMs plus the Pi 3 (`pi-worker`) are agents
- Each node registers under its inventory name (`node-name`), so `kubectl` shows the same names as Ansible and DNS whatever the OS hostname is
- Settings (k3s version, servicelb disabled, control-plane taint, kubeconfig context `k3s`) are in `ansible/group_vars/k3s_cluster.yaml`
- Needs `python-netaddr` and `kubectl` on the machine running Ansible

```bash
ansible-galaxy collection install -r requirements.yaml    # Once, and after changing the pin
ansible-playbook k3s.yaml                                 # Install; merges the kubeconfig into ~/.kube/config
ansible-playbook k3s.yaml -e k3s_server_serial=1          # Upgrade after bumping k3s_version, one server at a time
ansible-playbook k3s.orchestration.reset                  # Uninstall k3s from every node
```

## Gitea Users and Mirrors

`gitea/` is a separate OpenTofu root with its own state (`homelab/gitea/terraform.tfstate` in the same R2 bucket). The Gitea provider needs Gitea running, which only happens after the root apply and the Ansible playbook, so it can't live in the root config. It creates a user, an organisation (the admin and the user are both owners), the private pull mirrors in `gitea_mirrors` inside that organisation (by default `homelab-argocd-config`) and a read-only user ArgoCD pulls them with.

Run order on a rebuild:

```bash
tf apply                                  # root: containers, VMs, tunnel
cd ansible && ansible-playbook playbook.yaml && cd ..
tf -chdir=gitea init
tf -chdir=gitea apply                     # needs gitea/terraform.tfvars
```

After Gitea (and its Postgres) is rebuilt, the `gitea/` state still points at the old objects. The org, mirror and team membership notice they're gone and are recreated, but the provider errors on missing users (`user not found with id N`), so drop them from state first:

```bash
tf -chdir=gitea state rm gitea_user.owner gitea_user.argocd
```

`gitea/terraform.tfvars` (gitignored) sets `gitea_url`, `gitea_admin` (the admin's username and the root `gitea_admin.password`), `gitea_user` and `gitea_argocd_user` (each a username, an email no other user has, and a password) and `gitea_org` (organisation name).

## ArgoCD

`argocd/` is a third OpenTofu root with its own state (`homelab/argocd/terraform.tfstate`). It uses the Helm provider with the `k3s` kubeconfig context that `ansible/k3s.yaml` writes, and installs:

- `argo-cd` (argo-helm), with one credential template that logs in to every repo in the Gitea org as the read-only `argocd` user
- `argocd-apps` (argo-helm), creating the root Application ("app of apps") that syncs `argocd/applications/` from the Gitea mirror of `homelab-argocd-config`

Chart settings are plain values files in `argocd/values/` (`argo-cd.yaml`, `root-app.yaml`), with the Gitea URL written out as in `homelab-argocd-config`. The `argocd` username and password are read from the `gitea/` state and passed with `set_sensitive`, so that password only lives in `gitea/terraform.tfvars`. `argocd/terraform.tfvars` holds only `argocd_admin_password`, the UI `admin` password, which is stored bcrypt hashed. OpenTofu owns the ArgoCD install; ArgoCD owns everything it deploys.

```bash
tf -chdir=argocd init
tf -chdir=argocd apply
kubectl -n argocd port-forward svc/argocd-server 8080:443   # UI on https://localhost:8080, user admin
```

## Rebuild Runbook

Each step needs the one before it finished:

1. `tf apply` in the MikroTik repo
2. `tf apply` here (containers, VMs, tunnel)
3. `cd ansible && ansible-playbook playbook.yaml`
4. `ansible-playbook k3s.yaml` (the cluster)
5. `tf -chdir=gitea apply` (see Gitea Users and Mirrors for the `state rm` after a Gitea rebuild)
6. `tf -chdir=argocd apply`; ArgoCD then deploys everything in `homelab-argocd-config`

## Cluster Connectivity

pve01 and pve02 form one Proxmox cluster. OpenTofu reaches both through two connections, both configured in the `provider "proxmox"` block in `versions.tf`.

### API: one endpoint for the cluster

```
tofu ──HTTPS + API token──► pve01:8006 (proxmox.endpoint)
                               │
                               └── request for /nodes/pve02/... is forwarded ──► pve02
```

- `proxmox.endpoint` and `proxmox_auth.api_token` in `terraform.tfvars` point at pve01 only.
- Proxmox forwards any API request for another cluster node to that node ([pveproxy](https://pve.proxmox.com/pve-docs/pveproxy.8.html)), so pve02 needs no endpoint or token of its own. API users and tokens are cluster-wide.
- If pve01 is down, OpenTofu can't manage either node.

### SSH: one entry per node

The provider uses SSH for the few operations the API can't do, such as file uploads. The `ssh` block creates one `node {}` entry per node in `var.proxmox_nodes`, using its `address`, `proxmox.ssh_port` (2222) and `proxmox.ssh_user`, with keys from the SSH agent.

### Which node a resource lands on

Connecting to the cluster and placing a resource on a node are separate. Each resource names its own node:

| Resource | Node setting | Lands on |
|---|---|---|
| `module.proxmox_node` (APT repos, ZFS pool) | each key of `var.proxmox_nodes` | pve01 and pve02 |
| `proxmox_storage_zfspool.nvme_storage` | `nodes = keys(var.proxmox_nodes)` | cluster-wide entry for both |
| Download modules | each key of `var.proxmox_nodes` | pve01 and pve02 (`nvme-files` is local to each node) |
| `k3s_cluster` | `node_name` on each `k3s_vms` entry (required) | control_01 and workers 01–02 on pve01, control_02 and workers 03–05 on pve02 |
| `lxc_containers` | `node_name` on each `lxc_containers` entry, else `proxmox.node` in `terraform.tfvars` | pve01, except pulse, cloudflared and bind9 on pve02 (the second copies, `cloudflared_02` and `bind9_02`, are on pve01) |

Changing a guest's `node_name` migrates it rather than recreating it (`migrate = true`): VMs move live, containers restart on the new node. Each k3s VM clones the template on its own node.

### Where the node details live

- `terraform.tfvars`: the `proxmox` block (endpoint, default guest node, SSH user and port) and `proxmox_auth`. Only pve01's details are needed here.
- `variables.tf`: the `proxmox_nodes` default lists every node with its SSH address and ZFS pool disks. Adding a node to the cluster starts here.

## State Backend (Cloudflare R2)

State is stored remotely in a Cloudflare R2 bucket via OpenTofu's S3-compatible backend (`backend.tf`):

- **Bucket:** `iac-state`
- **Key:** `homelab/proxmox/terraform.tfstate`
- **Locking:** native S3 lockfile (`use_lockfile = true`), no DynamoDB needed
- **Region:** `auto` with AWS-specific validation checks skipped, as R2 is not AWS

Credentials and the R2 endpoint are not in `backend.tf`. They are supplied as environment variables from a local, gitignored `.envrc` loaded by [direnv](https://direnv.net/):

```bash
#!/usr/bin/env bash
export AWS_ACCESS_KEY_ID="<r2-access-key-id>"
export AWS_SECRET_ACCESS_KEY="<r2-secret-access-key>"
export AWS_ENDPOINT_URL_S3="https://<cloudflare-account-id>.r2.cloudflarestorage.com"
```

Create an R2 API token with Object Read & Write on the `iac-state` bucket, fill in `.envrc`, then:

```bash
direnv allow
tofu init
```
